# Benchmark Leakage Controls v1 — Next-Revision Plan

Status: design proposal for the next prospective benchmark revision.

This document does not amend or reinterpret the frozen V2 design, evidence, or
results. It defines controls to freeze before collecting any new model output.

## Purpose

Establish whether a benchmark pass reflects the intended task rather than a
shortcut available through the prompt, task surface form, oracle path, output
normalization, or repeated-request state.

The controls are construct-validity measurements. They do not improve scores,
repair outputs, alter router policy, or replace the independent semantic
oracle.

## Controls to add before the next run

### 1. Null baselines

Run deterministic, no-model baselines through the same normalization and oracle
path as model outputs:

- empty output;
- prompt echo;
- extracted input block;
- first and last prompt lines;
- longest word or capitalized span where the prompt format makes those
  strategies meaningful;
- constant labels for classification cohorts.

Record one result per task, variant, and baseline. A task passed by any null
baseline receives `CV_NULL_BASELINE_PASSES` and is excluded from capability and
routing-policy scoring until deliberately redesigned.

`extract_input_block` and any capitalized-span heuristic must be pure,
deterministic, and independently unit-tested. If the prompt format does not
support a reliable extraction, record that limitation rather than inventing a
heuristic.

### 2. Request-payload leakage test

Keep request construction dependent only on task identity and prompt. Add a
regression test that serializes every request payload and verifies that oracle
expected values do not appear outside the prompt field. Legitimately
prompt-derived expected strings are allowed inside `prompt` only.

The oracle must remain unavailable to the request-building module. The
correctness oracle runs only after raw output and telemetry have been captured.

### 3. Normalization delta telemetry

For every condition, record:

- `raw_output` and `normalized_output`;
- `normalization_applied`;
- `normalization_steps`;
- `oracle_correct_raw`;
- `oracle_correct_normalized`;
- `normalization_changed_verdict`.

The raw and normalized paths must be scored independently. Normalization must
remain narrow, explicit, and class-specific. No prose extraction, JSON key
repair, bullet-marker repair, or semantic correction is permitted.

### 4. Prompt ablation

Run each task with its input payload removed or deterministically shuffled while
preserving the instruction. Use the same model, oracle, normalization, and
repetition policy. Every ablated task is expected to fail.

Any ablated pass receives `CV_ABLATION_PASSES` and is excluded from capability
scoring. Ablation results are evidence about prompt answerability, not model
capability.

### 5. Human-authored mutation variants

Freeze at least one surface mutation per task before model execution. Mutants
must preserve task structure and difficulty while changing the source content
and expected value. They must be authored from the task structure, not
generated by a model.

Compare base and mutant outcomes:

| Base | Mutant | Code |
|---|---|---|
| pass | pass | `CV_OK` |
| pass | fail | `CV_MUTANT_DIVERGENCE` |
| fail | pass | `CV_MUTANT_DIVERGENCE` |
| fail | fail | `CV_OK` |

With small repetition counts, divergence is a flag for follow-up rather than
automatic proof of contamination. It must not be folded into a headline score
until resolved.

### 6. Repetition independence

Prove that every repetition uses a fresh request with no conversation history,
reused session identifier, or carried state. Disable prompt/KV caching where
possible or record cache state explicitly. Record repetition index and model
residency on each row.

Add tests showing that consecutive repetition payloads are identical except for
fields intentionally varied and that no state from repetition n appears in
repetition n+1.

## Machine-checkable run gate

A new benchmark may be labelled construct-valid only when all of the following
are true:

- preflight and model identity checks pass;
- telemetry invariants hold for every row;
- all null baselines ran for every task and variant;
- every scored task is `CV_OK`;
- no task passes input-removed or input-shuffled ablation;
- every task has at least one human-authored mutation;
- repetition-independence tests pass;
- request-payload oracle-leakage tests pass;
- raw and normalized correctness are both recorded;
- provider failures and instrumentation failures remain distinct;
- no canonical output is overwritten, resumed, or silently repaired.

Failure of a control is a benchmark-validity finding. The task is excluded or
the run is blocked according to the frozen protocol; it is not edited to make
the control pass within the same experiment.

## Reporting rules

Every report must keep these layers separate:

1. contract or format conformance;
2. operational gate survival;
3. raw-output and normalized-output oracle correctness;
4. construct-validity status from baselines, ablations, and mutants.

Classification contracts continue to test permitted-label conformance, not
semantic correctness. Executable transformations continue to be reported as a
separate deterministic-executor analysis rather than validator evidence.

Retrospective controls may describe the frozen observations, but they must not
be presented as unbiased prospective estimates for unseen tasks or models.

## Execution order

1. Review and freeze the next suite, oracle, contracts, variants, and this
   control design.
2. Authenticate hashes and model identities.
3. Implement and test the controls with no provider calls.
4. Run null baselines and static leakage checks.
5. Run model, ablation, and mutant conditions under immutable output rules.
6. Analyze only after all control statuses are machine-checked.
7. Write an audit that reports exclusions, normalization dependence, and all
   deviations explicitly.

No current V2 canonical artifact is modified by this plan.
